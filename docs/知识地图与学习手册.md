## 2. 第一层：HTTP 协议（一切的根）

### 2.1 一个请求到底是什么

**概念**：HTTP 是文本协议。一个请求在网络上是这样一串字节：

```
GET /eportal/portal/login?user_account=,1,2023xxxx&user_password=*** HTTP/1.1
Host: 10.0.0.1:801
User-Agent: Mozilla/5.0 (Linux; Android 16) ...
Accept: */*
Cookie: JSESSIONID=xxx
Connection: close

```

四段，用 `\r\n` 分隔，最后空一行：

1. **请求行**：`方法 路径?查询 协议版本`
2. **请求头**：`键: 值`，一行一个
3. **空行**：`\r\n\r\n`，表示头部结束
4. **请求体**：GET 通常没有，POST 才有

响应长得对称：

```
HTTP/1.1 302 Found
Location: http://10.0.0.1/a79.htm
Set-Cookie: JSESSIONID=xxx; Path=/
Content-Length: 0

```

**本项目落点**：`core/Http.java` 里所有请求都经过同一个方法（约 175–230 行），它显式设了 `setInstanceFollowRedirects(false)`、`User-Agent`、`Cookie`、`Content-Type`，然后按 `r.code >= 400` 决定读 `getErrorStream()` 还是 `getInputStream()`。

**吃透它要会什么**

- 能手写一个 `curl -v` 并读懂它的输出
- 知道 `Host` 头为什么存在（一个 IP 上跑多个站）
- 知道 `Content-Length` 和 `Transfer-Encoding: chunked` 的区别
- 知道为什么 `r.code >= 400` 时 `getInputStream()` 会抛异常

**常见误区**：以为「请求失败 = 网络不通」。我们这次 203 那个 bug 就是反例：**服务器回了 203 和一段 JSON，网络完全正常，只是业务失败**。HTTP 层面的成功和业务层面的成功是两件事，这个观念后面会反复出现。

---

### 2.2 状态码：204、302、203 各自意味着什么

这是本 app 判定「在不在线」的全部依据，值得单独讲。

| 码 | 语义 | 在本项目里的含义 |
|---|---|---|
| `204 No Content` | 成功，但**故意不返回任何内容** | **已认证**。探测点 `generate_204` 就该回这个 |
| `302 Found` | 临时重定向，看 `Location` | **未认证**。网关把你劫持到登录页 |
| `200 OK` | 成功且有内容 | 要看内容是什么：是门户页 = 未认证 |
| `203` | 非权威信息 | 这里其实是锐捷返回的**业务错误**（`Error code: 203 Bad request(2)`），不是标准语义 |
| `502/504` | 网关错误 | 网关自己挂了，既不在线也不像门户 |

**为什么用 204 探测**：`generate_204` 这个 URL 是 Google/小米/高通共同约定的「连通性探测点」。设计意图极简——服务器只要活着就返回一个空 204。安卓系统自己也用它判断「这个 Wi-Fi 有没有网」。

**本项目落点**：`core/Judge.java:82`

```java
public static boolean online(Http.Result r) {
    if (r.code == 204 || r.code == 205) return true;
    ...
    // 真正的 204 探测点正常应无 body；有 HTML 一定是被劫持的登录页
}
```

注意第二段那句注释，它是第二个 bug 的修复：**有些网关不老实，会返回 `200 + 登录页 HTML`**，如果你只看「2xx 就是成功」就会误判成已登录。

**吃透它要会什么**

- 记住 1xx/2xx/3xx/4xx/5xx 五类的划分依据
- 知道 301 和 302 的区别（永久 vs 临时，会不会被缓存）
- 知道 204 和 200 空 body 的区别（204 要求不能有 body，200 可以有）

**常见误区**：「2xx 就是成功」。在强制门户环境下这句话是错的，因为劫持者可以让任何请求都返回 200。

---

### 2.3 GET 和 POST 的真正区别

教科书会说「GET 取数据，POST 提交数据」。这句话在本项目里正好被推翻：**锐捷的登录请求是 GET**。

```
GET /eportal/portal/login?user_account=...&user_password=...&wlan_user_ip=...
```

账号密码全在 URL 里。这是真实抓到的包，不是设计失误——很多老系统就是这样。

真正的区别在协议语义上：

| | GET | POST |
|---|---|---|
| 参数位置 | URL 的 query 部分 | 请求体 |
| 幂等性 | 语义上幂等（重复执行结果一样） | 不保证 |
| 缓存 | 可被缓存 | 默认不缓存 |
| 长度限制 | 受 URL 长度限制（浏览器约 2KB–8KB） | 基本无限制 |
| 日志/历史 | 会进服务器访问日志、浏览器历史 | 不进 |
| 安全性 | **参数可见** | 参数在 body（但明文 HTTP 一样能抓） |

**为什么「密码放 URL」很危险**：URL 会进 nginx access log、进代理日志、进浏览器历史、进 Referer 头。我们这次抓到的包之所以能拿到明文密码，正是因为它在 URL 里。

**本项目落点**：`core/EportalQuery.java` 构造 query string；`core/Http.java` 的 `postForm` 和 `postRaw` 处理表单和原始 body。

**吃透它要会什么**

- 能说出「为什么登录应该用 POST」的三条理由
- 知道 `application/x-www-form-urlencoded` 和 `multipart/form-data` 的区别
- 知道 `multipart/form-data` 里 boundary 是干什么的

### 2.4 URL 编码：为什么参数里会有一堆 `%XX`

**概念**：URL 里只有一部分字符是安全的（字母、数字、`-_.~`）。其他字符必须转成 `%十六进制`。

两个不同的编码函数，别搞混：

| 函数 | 空格编成 | 用在 |
|---|---|---|
| `URLEncoder.encode(s, "UTF-8")` | `+` | **query string / 表单** |
| `Uri.encode(s)` | `%20` | **URL 路径段** |

Java 的 `URLEncoder` 是专为 `application/x-www-form-urlencoded` 设计的，所以空格编成 `+`。如果你拿它去编路径，服务器的路径解析器会认为那是真的加号。

**本项目落点**：锐捷那个 `user_account=,1,<账号>` 里的逗号会被编成 `%2C`；`v=10420` 那种随机数是防缓存。

**吃透它要会什么**

- 手算 `"a b"` → `a+b` 和 `a%20b`
- 知道中文 UTF-8 编码后为什么是 3 个字节 → 9 个字符（`%E4%B8%AD`）
- 知道双重编码 bug 长什么样（`%25E4` 这种）

**常见误区**：以为编码只有一种。锐捷的 `user_account` 里那个 `,1,` 前缀——逗号在某些实现里不编也能过，但在严格实现里必须编。**这类「编不编都能跑」的地方，是逆向时最容易出错的地方**：你以为参数错了，其实是编码方式不同。

### 2.5 Cookie：无状态协议怎么记住你

**概念**：HTTP 本身不记人。会话靠两样东西维持：

1. **Cookie**：服务器 `Set-Cookie: JSESSIONID=abc`，客户端之后每次请求带 `Cookie: JSESSIONID=abc`
2. **服务端会话表**：那个 ID 在服务器内存里对应一个 session 对象

流程：

```
客户端                     网关
  |  GET /login   →
  |                ←  302 + Set-Cookie: JSESSIONID=abc
  |  GET /portal  →  Cookie: JSESSIONID=abc
  |                ←  200 已登录
```

**为什么 portal 认证需要 Cookie**：锐捷的 ePortal 是**两阶段**的：先拿一个会话（JSESSIONID），再带着这个会话去登录。如果第二步丢了 Cookie，服务器认不出你是刚才那个人，就会报「参数错误」。

**本项目落点**：`core/Http.java:73-115`，自己实现了一个极简 CookieJar：

- `cookieHeader(url)`：按 URL 取要发的 Cookie
- `storeCookies(url, conn)`：从响应的 `Set-Cookie` 里提取并存储

为什么不用 `CookieManager`？因为我们要**精确控制**哪些请求带 Cookie——探测请求不该带 campus 的会话 Cookie（会污染），登录请求必须带。

**吃透它要会什么**

- 知道 `Set-Cookie` 的 `Path` / `Domain` / `Expires` / `HttpOnly` / `Secure` 各管什么
- 知道 `HttpOnly` 是为了防 XSS 偷 Cookie
- 知道 `Secure` 要求 HTTPS
- 能写出一个「按 domain+path 匹配」的 Cookie 选择逻辑

**常见误区**：以为 Cookie 就是「一个字符串随便带」。真实实现里 domain 匹配规则（`example.com` 能不能匹配 `a.example.com`）、path 匹配规则（`/a` 能不能匹配 `/ab`）都有坑。

### 2.6 字符集：为什么国内 portal 大量是 GBK

**概念**：字节 → 字符需要一张映射表。UTF-8 和 GBK 是两张不同的表，同一串字节用不同的表解出来就是乱码。

问题在于：**很多国内 portal 返回 GBK 编码的页面，但响应头里不写 `charset`**。

**本项目落点**：`core/Http.java:268-305`，`decode()` 方法做了三级兜底：

```java
// 1. 先看 Content-Type 里的 charset
// 2. 再看 HTML 里的 <meta charset="gbk">
// 3. 都没有 → 依次尝试 UTF-8 / GBK / ISO-8859-1，哪个不产生替换字符就用哪个
```

这个「试解码」技巧值得记住：UTF-8 对非 ASCII 字节有严格的结构要求（首字节 `110xxxxx` 表示 2 字节序列等），非法序列会产生 `U+FFFD`。所以「解出来没有 `U+FFFD` 就是对的编码」是个可靠启发式。

**吃透它要会什么**

- 知道 ASCII / GBK / UTF-8 / UTF-16 的字节结构
- 知道 `ISO-8859-1` 的特殊性质：**它对任意字节序列都不报错**（1 字节 = 1 字符），所以它永远能「成功」解码，也永远不该是首选
- 能用 Java 写出「试解码」逻辑

**常见误区**：直接 `new String(bytes)`，用平台默认编码。在 Windows 上是 GBK、在 Linux 上是 UTF-8，同一份代码在两台机器结果不同——这是最经典的跨平台 bug 来源。

### 2.7 JSONP：为什么响应长成 `dr1003({...})`

**概念**：JSONP 是 2010 年代绕开同源策略的土办法。

正常 JSON：

```json
{"result": "success", "userIndex": "123"}
```

JSONP：

```javascript
dr1003({"result": "success", "userIndex": "123"})
```

原理：`<script>` 标签不受同源策略限制，可以加载任意域的 JS。所以服务器把数据包进一个函数调用里，前端预先定义 `function dr1003(data){...}`，脚本一加载就自动执行，数据就到手了。

`dr1003` 里的 `1003` 是**随机数**，由请求的 `callback=dr1003` 参数指定，服务器原样回显。

**本项目落点**：`core/Jsonp.java` 负责剥壳——把 `dr1003(` 和 `)` 去掉，剩下的当 JSON 解析。**这个类刻意写成纯 Java 无 Android 依赖，所以能在桌面 JVM 上跑单测**（第 9 章会讲这个设计的意义）。

**吃透它要会什么**

- 说清楚 JSONP 为什么能跨域，以及它为什么被 CORS 取代
- 知道 JSONP **只能 GET**（`<script src>` 只能发 GET）
- 能处理边界：回调名里带点（`foo.bar`）、响应里前后有空白、服务器返回 JSON 数组

**常见误区**：用正则 `^dr1003\((.*)\)$` 一把梭。遇到响应体里本身含括号就崩。正确做法是**找第一个 `(` 和最后一个 `)`**，而不是贪婪匹配。

### 2.8 User-Agent 与设备指纹

**概念**：UA 是浏览器/客户端自报家门的字符串。服务器常拿它做分流：PC 版页面、手机版页面、App 专用接口。

锐捷那个请求里有 `terminal_type=2`，这个 `2` 通常表示「移动端」。如果值不对，服务器可能返回 PC 版页面或者直接拒绝。

**本项目落点**：`core/Http.java:34` 定义了一个 Android UA 常量，所有请求统一带。

```java
public static final String UA_ANDROID = "Mozilla/5.0 (Linux; Android ...) ...";
```

**吃透它要会什么**

- 读懂一条真实 UA 的每一段（平台、渲染引擎、浏览器、版本）
- 知道为什么爬虫要伪装 UA
- 知道 UA 不可信（客户端自报，随便改）

## 3. 第二层：Captive Portal 强制门户

这一层是本项目真正的领域知识。不懂这一层，前面学的 HTTP 全是空转。

### 3.1 什么是 Captive Portal

**概念**：你连上 Wi-Fi 了（链路层通了），但还不能上网（网络层被拦）。所有 HTTP 请求被网关拦下来，重定向到一个登录页。登录之后网关放行你的 IP/MAC。

```
手机                    网关（10.0.0.1）           外网
   |                        |                          |
   |-- GET generate_204 --->|                          |
   |                        |  未认证 → 拦截            |
   |<-- 302 /a79.htm ------|                          |
   |-- GET /a79.htm ------>|                          |
   |<-- 200 登录页 ---------|                          |
   |                        |                          |
   |    [登录成功]           |                          |
   |-- GET generate_204 --->|-- 放行 ------------------>|
   |<-- 204 ----------------|<-- 204 -------------------|
```

关键点：**「能不能上网」和「连没连上 Wi-Fi」是两件事**。这就是 1.0.1 那个「开流量时显示已登录」bug 的根源。

### 3.2 接入控制的三代技术

| 代 | 技术 | 工作层 | 典型场景 |
|---|---|---|---|
| 1 | PPPoE 拨号 | 数据链路层 | 老式宿舍宽带 |
| 2 | 802.1X | 数据链路层（EAPoL） | 企业/高校有线网，锐捷起家于此 |
| 3 | **Web Portal** | 应用层 | 现在的校园 Wi-Fi 主流 |

**为什么是 Web Portal 赢了**：不需要装客户端、不需要系统支持 802.1X 认证器、任何有浏览器的设备都能用。

**为什么 Web Portal 麻烦**：认证逻辑全在网页里，各家实现完全不同。所以「自动登录」的本质是「自动完成一次网页表单提交」。

### 3.3 网关劫持是怎么做到的

四种手法，从粗暴到精细：

1. **DNS 劫持**：把 `connect.rom.miui.com` 解析到网关自己的 IP
2. **HTTP 302 重定向**：正常解析 DNS，但拦截你的 HTTP 请求，回 302 到登录页
3. **透明代理**：请求到达网关，它代替你去请求，拿到响应后替换成登录页
4. **TCP 层重置**：直接 RST 掉你的连接（体验最差）

本项目遇到的是第 2、3 种：探测请求被 302 到 `a79.htm`。

**关键认知**：劫持只针对 **HTTP（80 端口）**。HTTPS 有证书校验，网关没法伪造（除非用户装了它的根证书）。所以：

- `http://connect.rom.miui.com/generate_204` → **会被劫持**，返回登录页
- `https://www.google.com/generate_204` → 不会被劫持，但**连接会超时/失败**

这解释了一个隐蔽的坑：**如果探测点用 HTTPS，未认证时你拿到的是「连接失败」而不是「重定向」**，程序很可能把「失败」误判成「网络异常」而不是「未认证」。

### 3.4 Guard：为什么凭据不能发往探测点

**这是 1.0.5 修的 bug，也是本项目最重要的一课。**

**事故经过**：早期实现里，「探测失败 → 把落点地址当作门户 → 提交表单」。当探测请求本身失败（超时、DNS 失败）时，落点地址仍然是 `http://connect.rom.miui.com/generate_204`。于是账号密码被 POST 到了小米的服务器。

**根因**：`PortalProbe` 在「传输失败」的情况下仍然返回了 `portalUrl`（因为落点地址总存在），下游把「落点地址」当成了「确认的门户地址」。

**修复**：`core/Guard.java` 做了一件事——**在提交凭据之前，校验目标地址**：

```java
public static boolean maySubmitCredentials(String target, String probeUrl) {
    // 1. 目标是已知的连通性探测点（小米/Google/Apple/微软/高通/vivo/华为/Firefox）
    //    → 拒绝
    // 2. 目标是探测点本身（和 probeUrl 同主机同路径）
    //    → 拒绝
    // 3. 目标是 generate_204 / hotspot-detect.html / ncsi.txt 这类约定路径
    //    → 拒绝
    // 否则放行
}
```

并在**三个**提交口都加了这道闸门：`FormAuth`、`EportalWebAuth`、`PortalActivity`。单点防御是没用的，必须每个出口都查。

**这一课的一般化**：**任何「把用户凭据发出去」的代码路径，都要有一个集中的、默认拒绝的出口检查**。不要指望每个调用点都记得判断。

**吃透它要会什么**

- 列出主流厂商的探测点（这是网络环境指纹的一部分）
- 理解「默认拒绝」（fail-closed）和「默认放行」（fail-open）的安全差异
- 能设计一个「凭据去处白名单」而不是黑名单

**为什么白名单更好**：黑名单永远漏。你列举了 8 个探测点，第 9 个就漏了。但这里用黑名单是**权衡后的选择**——因为门户地址是任意的（100.64.x.x、10.x.x.x、甚至公网 IP 都可能），没法预先白名单。所以实际做法是「黑名单 + 结构性判断（是不是探测点/是不是探测路径）」。

### 3.5 在线判定的三层逻辑

`core/Judge.java` 把「在不在线」拆成三层，顺序不能反：

```java
// 第一层：物理层——Wi-Fi 在不在
if (!hasWifi) {
    // 即使移动数据能上网，也必须返回 online = false
    return noWifi(hasCellular);
}

// 第二层：传输层——探测请求成不成功
if (transport failed) { online = false; }

// 第三层：应用层——响应像不像「真的通了」
online = online(r);   // 204/205 无 body → true；否则 false
```

**第一层为什么必须最先**：手机同时有 Wi-Fi 和移动数据时，`HttpURLConnection` 默认走**系统默认网络**。如果 Wi-Fi 没认证，系统会自动切换到移动数据，于是探测请求成功返回 204——**看起来已登录，实际走的是流量**。这就是 1.0.1 那个 bug。

修复方式是两层保险：

1. `Judge` 里先查 Wi-Fi 状态
2. `Net.bindProcessToWifi()` 把进程强制绑到 Wi-Fi 网络，让请求物理上不可能走流量

### 3.6 探测点为什么有好几个

系统级连通性探测是**厂商各自实现**的：

| 厂商 | 探测地址 | 期望响应 |
|---|---|---|
| Google | `http://connectivitycheck.gstatic.com/generate_204` | 204 |
| 小米 | `http://connect.rom.miui.com/generate_204` | 204 |
| Apple | `http://captive.apple.com/hotspot-detect.html` | 200 + 特定 HTML |
| 微软 | `http://www.msftconnecttest.com/connecttest.txt` | 200 + `Microsoft Connect Test` |
| 华为/荣耀 | `http://connectivitycheck.platform.hicloud.com/generate_204` | 204 |
| vivo | `http://wifi.vivo.com.cn/generate_204` | 204 |
| Firefox | `http://detectportal.firefox.com/success.txt` | 200 + `success` |

`Guard` 里的黑名单就是照这张表来的。

**为什么需要这张表**：不只是为了拦截误发，也是为了**识别**——如果你看到一个请求发往 `connect.rom.miui.com`，那它不是门户，是系统在自检。

### 4.3 读懂一个抓到的请求

```
GET http://10.0.0.1:801/eportal/portal/login
    ?callback=dr1003
    &login_method=1
    &user_account=,1,<账号>
    &user_password=<密码>
    &wlan_user_ip=<本机IP>
    &wlan_user_mac=000000000000
    &wlan_ac_ip=10.0.0.2
    &jsVersion=4.1.3
    &terminal_type=2
    &v=10420
```

逐个参数的含义（这些是**推断**，但有依据）：

| 参数 | 含义 | 依据 |
|---|---|---|
| `callback=dr1003` | JSONP 回调名 | 响应体是 `dr1003({...})` |
| `login_method=1` | 登录方式：账号密码 | 其他值未探 |
| `user_account=,1,xxx` | 账号，`,1,` 是「账号类型」前缀 | 常见约定：1=学号 |
| `user_password` | 密码明文 | 值直接就是密码 |
| `wlan_user_ip` | 本机在校园网的 IP | 值 = `Net.wifiIp()` |
| `wlan_user_mac` | MAC，全 0 表示由网关自己取 | 全 0 是「让服务端查 ARP」的约定 |
| `wlan_ac_ip` | AC（无线控制器）地址 | `10.0.0.2`，和网关 `.17` 相邻 |
| `jsVersion=4.1.3` | 前端脚本版本 | 门户页里的版本号 |
| `terminal_type=2` | 终端类型：2=移动端 | PC 通常是 1 |
| `v=10420` | 随机数，防缓存 | 每次不同 |

**怎么推断这些含义**：看**值的变化规律**。

- 每次请求都变的 → 随机数/时间戳
- 和你手机 IP 一致的 → 本机 IP
- 和账号一致的 → 账号
- 固定的常量 → 版本号/枚举值
- 响应里回显的 → 回调名

**这一课的一般化**：逆向参数不要猜名字，**看值**。名字可能是 `user_account`，也可能是 `ua`、`acc`、`username`；但值是学号这个事实不会变。

### 4.4 挑战-响应：深澜 srun 的两阶段认证

深澜比锐捷复杂一个量级，它有真正的密码学设计。

```
第一阶段：拿挑战
客户端 →  GET /cgi-bin/get_challenge?callback=x&username=xxx&ip=xxx
服务器 ←  {"challenge": "随机字符串", "client_ip": "...", ...}
                    ↓
            这个 challenge 就是后面所有签名的密钥

第二阶段：提交
客户端 →  GET /cgi-bin/srun_portal
           ?action=login
           &username=xxx
           &password={MD5}<HMAC-MD5(密码, challenge)>
           &info={SRUN}<自定义base64(XXTEA(json, challenge))>
           &chksum=<HMAC-MD5(拼接串, challenge)>
           &ac_id=1&ip=xxx&n=200&type=1&enc=srun_bx1
服务器 ←  {"suc_msg": "login_ok", ...}
```

**为什么这么设计**：密码不能明文传（防抓包），但客户端又不能存密钥（会被逆出来）。解法是——**密钥每次由服务器临时发**。挑战只能用一次，用完作废。

**本项目落点**：`auth/SrunCrypto.java`

```java
// info 参数：{SRUN} + 自定义base64(XXTEA(json, encVer))
public static String buildInfo(String username, String password, String ip, ...) {
    return "{SRUN}" + base64(xencode(json, Str.nz(encVer, "srun_bx1")));
}

// 校验串 = username + HMAC-MD5(password, token) + acid + ip + n + type + info
// 再对整串做 HMAC-MD5，密钥仍是 token
public static String checksum(...) { ... }
public static String passwordHmd5(String password, String token) { ... }
```

**吃透它要会什么**

- 理解「密钥交换」和「预共享密钥」的区别
- 理解为什么挑战-响应能防重放（每次挑战不同）
- 能读懂 `{SRUN}` 这种「协议标记前缀」的设计意图（服务端据此选解密路径）

### 4.5 自动识别：把逆向过程写成程序

本项目最巧妙的设计：**不硬编码任何一家厂商，而是「探测 → 解析 → 推断 → 尝试」**。

```
1. 请求探测点
2. 没被劫持（204）→ 已在线，结束
3. 被劫持 → 顺着重定向链走，拿到门户页 HTML
4. 解析 HTML：
   - 找 <form> → 拿到 action / method / 所有 <input> 的 name
   - 找 <iframe> → 说明登录框在子页（本项目 a79.htm 就是这种）
   - 找关键词 → 识别厂商（srun / eportal / drcom / 通用）
5. 推断：提交地址、用户名字段名、密码字段名
6. 按厂商优先级串行尝试认证器
```

**为什么这比硬编码强**：换一所学校，只要门户结构不是全新范式，这套逻辑就能跑。而硬编码的代码换学校必死。

**为什么这还不够**：a79.htm 里 `<form>` 数量是 **0**——账号密码框是 JS 动态渲染的。静态 HTML 解析拿不到任何东西。所以必须有 WebView 兜底（第 7 章）。

**本项目落点**：`core/PortalProbe.java:211-265`

```java
// 落点是探测地址 + 页面没有门户特征 → 网关根本没劫持，别瞎填
if (Guard.isConnectivityCheck(url) && !looksLikePortal(html)) {
    ...
}
parseForms(html, url, out.forms);
detectVendor(url, html, out);
if (out.forms.isEmpty()) {
    // 无表单 + 有 iframe = 登录框在子页面
    List<String> iframes = iframeClues(html);
}
```

## 5. 第四层：密码学（读到能读懂，不要求发明）

### 5.1 三个概念别搞混

| | 加密 Encrypt | 哈希 Hash | 签名/HMAC |
|---|---|---|---|
| 可逆 | **能解回原文** | 不能（单向） | 不能 |
| 输出长度 | 和输入相关 | 固定 | 固定 |
| 密钥 | 需要 | 不需要 | 需要 |
| 用途 | 保密 | 完整性校验（非安全） | 完整性 + 身份认证 |
| 本项目 | XXTEA | MD5 | HMAC-MD5 |

**关键区分**：`MD5(密码)` 和 `HMAC-MD5(密码, 密钥)` 完全不同。前者任何人都能算（因为算法公开），后者必须有密钥。所以**存密码用哈希，传密码用 HMAC**。

### 5.2 XXTEA：为什么是它

**概念**：TEA（Tiny Encryption Algorithm）是 1994 年剑桥的 David Wheeler 和 Roger Needham 设计的极简分组密码。XXTEA 是它的修正版，解决了 TEA 的等效密钥攻击问题，并且支持**任意长度**分组（TEA 只支持 64 位）。

核心结构（`auth/SrunCrypto.java:97`）：

```java
int delta = 0x9E3779B9;   // = 2654435769 = floor(2^32 / φ)
```

这个常数是**黄金分割比**乘以 2³² 取整。为什么用黄金分割？因为在纯整数运算里，它能让每轮加法的进位分布最均匀——这是密码学里「用无理数生成伪随机」的经典手法。

XXTEA 加密一轮的伪代码：

```
sum += delta
for each word v[i]:
    v[i] += MX
    where MX = ((v[i-1]>>>5 ^ v[i+1]<<2) + (v[i+1]>>>3 ^ v[i-1]<<4)) ^ ((sum ^ v[i+1]) + (key[...] ^ v[i-1]))
```

看着吓人，其实就三件事：**移位（`>>>5`、`<<2`）制造雪崩、异或（`^`）混合、加法（`+`）扩散进位**。

**本项目落点**：`SrunCrypto.xencode()` 和 `xdecode()`（97–160 行）。`xdecode` 是逆运算，**只用于离线自测**——用来验证「加密再解密能拿回原文」，这是检验实现正确性的最直接办法。

**为什么能桌面自测**：`SrunCrypto` 零 Android 依赖（刻意自己实现 Base64 而不用 `android.util.Base64`），所以能在电脑 JVM 上直接跑。

### 5.3 Base64：6 bit 分组，和「自定义字母表」

**概念**：Base64 把 3 个字节（24 bit）拆成 4 个 6-bit 数，每个数查表映射成一个可打印字符。

```
原始：  01001101 01100001 01101110   ("Man")
分组：  010011 010110 000101 101110
索引：    19     22      5     46
映射：    T      W      F     u
结果：  "TWFu"
```

标准字母表是 `A-Za-z0-9+/`。深澜把这张表**重排**了（`SrunCrypto.java:23`）：

```java
private static final String STD_B64  = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/";
private static final String SRUN_B64 = "LVoJPiCN2R8G90yg+hmFHuacZ1OWMnrsSTXkYpUq/3dlbfKwv6xztjI7DeBE45QA";
```

同样是 64 个字符，只是顺序不同。映射方式（第 33–37 行）：

```java
char ch = std.charAt(i);
int idx = STD_B64.indexOf(ch);      // 在标准表里的位置
sb.append(SRUN_B64.charAt(idx));    // 换成深澜表里同位置的字符
```

**这个操作是加密吗？不是。** 这是**混淆**——算法完全公开，任何知道这张表的人都能立刻还原。它的作用是「让随手抓包的人看不懂」，不是「让攻击者解不开」。

**这个区分很重要**：混淆 ≠ 加密。判断标准是「密钥在哪」。密钥在客户端里 = 混淆；密钥在服务端 = 加密。

**本项目落点**：`stdBase64()` 是自己实现的（第 45 行起），而不是调用 `android.util.Base64`，理由写在注释里——**为了能在桌面 JVM 上做回归测试**。这是一个值得学的工程决策：为了可测性，宁可多写 30 行。

### 5.4 HMAC-MD5：为什么不能直接 md5(密码)

**概念**：HMAC = Hash-based Message Authentication Code。

```
HMAC(K, m) = H( (K ⊕ opad) || H( (K ⊕ ipad) || m ) )
```

其中 `ipad = 0x36` 重复 64 次，`opad = 0x5c` 重复 64 次。

**为什么这么绕**：直接 `H(K || m)` 有「长度扩展攻击」——知道 `H(K||m)` 的人可以在不知道 K 的情况下算出 `H(K||m||附加数据)`。HMAC 的两层结构把这个洞堵上了。

**本项目落点**：`SrunCrypto.passwordHmd5(password, token)` → 传的不是密码本身，是 `HMAC-MD5(密码, 挑战)`。所以网络上抓不到密码，重放也用不了（挑战每次都变）。

**MD5 已经不安全了，为什么还在用**：MD5 的「碰撞攻击」（找到两个不同输入有相同哈希）确实已破，但 HMAC-MD5 **没有**被破——因为攻击者不知道密钥，无法构造碰撞。所以在挑战-响应场景里，HMAC-MD5 至今仍算安全。

**这是密码学里最常见的误解之一**：「MD5 不安全」说的是抗碰撞性，不是所有用 MD5 的地方都不安全。要看具体用法。

### 5.5 该学到什么程度

你不需要能设计密码算法（**千万别自己设计**）。你需要的是：

1. **看到一段加密代码，能判断它属于哪一类**（对称/非对称/哈希/编码）
2. **能判断它的强度是否真实**（密钥在客户端 = 混淆，不是加密）
3. **能判断它防住了什么攻击**（防抓包？防重放？防篡改？）
4. **能判断它没防住什么**（比如本项目 portal 是明文 HTTP，密码在 URL 里，抓包即得）

第 4 点最重要。这套系统的密码学是**逐层递减**的：深澜有真密码学，锐捷 ePortal 是明文 URL 传密码，纯 HTTP。也就是说——**同一个 app，对不同学校的安全等级完全不同**。这也是本项目反复强调要改密码的原因。

## 6. 第五层：Android 应用开发

### 6.1 四大组件，本项目用了三个

| 组件 | 作用 | 本项目 |
|---|---|---|
| **Activity** | 一个界面 | `MainActivity`（首页）、`SettingsActivity`（设置）、`LogActivity`（日志）、`PortalActivity`（手动兜底网页） |
| **Service** | 后台长时间运行，无界面 | `WatchdogService`（前台服务，守护） |
| **BroadcastReceiver** | 接收系统/应用广播 | `BootReceiver`（开机自启） |
| ContentProvider | 跨应用数据共享 | 间接用到（`FileProvider` 是它的子类） |

### 6.2 前台服务：为什么必须「前台」

**背景**：Android 从 8.0（API 26）开始严格限制后台服务。App 退到后台后，普通 `Service` 会在几分钟内被系统杀掉。

**解法**：`startForeground()` + 一条**常驻通知**。有通知 = 用户知情 = 系统允许你活。

```java
// WatchdogService
startForeground(NOTIFY_ID, buildNotification());
```

**从 8.0 到 14 的限制演进**（这是必须知道的版本史）：

| 版本 | 变化 | 影响 |
|---|---|---|
| 8.0 | 后台服务受限，必须 `startForeground` | 不调就崩 |
| 9.0 | 必须声明 `FOREGROUND_SERVICE` 权限 | 漏声明就崩 |
| 10 | 后台启动 Activity 受限 | 不能随便弹页面 |
| 12 | **禁止从后台启动前台服务** | 只能在「用户可见时」或「收到特定广播时」启动 |
| 13 | 通知需要 `POST_NOTIFICATIONS` 运行时权限 | 用户拒绝 = 没通知 = 服务会被降级 |
| 14 | 前台服务必须声明**类型**（`foregroundServiceType`） | 要写清是 `dataSync` 还是 `specialUse` |

本项目在 `AndroidManifest.xml` 里给服务声明了类型，并用了 `IMPORTANCE_LOW` 的通知渠道。

**通知渠道（NotificationChannel）**：8.0 起，通知必须先建渠道，渠道的重要性决定表现：

```java
new NotificationChannel(CHANNEL_ID, "守护状态", NotificationManager.IMPORTANCE_LOW);
```

`IMPORTANCE_LOW` = 不响铃、不震动、不亮屏、不出浮窗，只在通知栏静静躺着。这正是守护进程需要的——每分钟更新一次状态，但用户不该被打扰。

**重要细节**：通知渠道的重要性**创建后不能改**。用户手动改过之后，代码设什么都不生效。所以渠道 ID 要在设计时想清楚，改重要性只能换新 ID。

### 6.3 Handler / Looper / MessageQueue：Android 的心跳

**概念**：Android 主线程是一个死循环：

```
Looper.loop() {
    while (true) {
        Message msg = queue.next();   // 没消息就阻塞
        msg.target.dispatchMessage(msg);
    }
}
```

`Handler` 是往这个队列塞消息的工具。`Handler.postDelayed(r, 60000)` = 「60 秒后把 r 塞进队列」。

**为什么不能用 `Thread.sleep()`**：阻塞主线程 = ANR（应用无响应）。所有定时任务必须走消息队列。

**本项目的用法**（`WatchdogService`）：

```java
handler.postDelayed(this::tick, intervalSec * 1000L);
```

而不是 `while(true) { check(); sleep(60s); }`——因为后者要占一个线程，而且无法被及时取消。

### 6.4 `View.postDelayed` 的陷阱（1.0.3 那个致命 bug）

**这是整个项目最有教育意义的一个 bug。**

**现象**：WebView 明明加载了门户页，但填表脚本**一次都没执行**。日志里没有一行来自 JS 的输出。

**代码原本是这样**：

```java
webView.postDelayed(() -> webView.evaluateJavascript(INJECT_JS, null), 1500);
```

**为什么没执行**：`View.postDelayed()` 的实现是这样的——

```java
public boolean postDelayed(Runnable action, long delayMillis) {
    Handler handler = mAttachInfo != null ? mAttachInfo.mHandler : null;
    if (handler == null) {
        // ★ 没有 attach 时，任务被扔进一个静态的 RunQueue
        getRunQueue().postDelayed(action, delayMillis);
        return true;
    }
    return handler.postDelayed(action, delayMillis);
}
```

而那个静态 `RunQueue` 里的任务，**只有在这个 View 被 attach 到窗口时才执行**（`dispatchAttachedToWindow` 时会 flush）。

**本项目的情况**：WebView 是**隐藏的**（为了不打扰用户），从来没有 `addView` 到任何容器，所以永远不 attach。于是：

- `postDelayed` 返回 `true`（以为是排队成功了）
- 实际上任务躺在静态 RunQueue 里，**永远不执行**
- 没有任何异常、没有任何日志

**这是最难查的一类 bug：静默失败。** 返回值是 true，代码不报错，就是不干活。

**修复**（1.0.3）：

```java
// 用 Handler 而不是 View.postDelayed
private final Handler handler = new Handler(Looper.getMainLooper());
handler.postDelayed(() -> webView.evaluateJavascript(INJECT_JS, null), 1500);
```

`Handler` 直接操作消息队列，不关心 View 有没有 attach。但还有第二个问题：**`evaluateJavascript` 在页面没加载完时调用会静默丢弃**。所以 1.0.3 还改成了**轮询驱动**：

```
每 400ms 检查一次：
  页面加载完了吗？（onPageFinished 标记）
  → 没完 → 下一轮
  → 完了 → 注入 → 检查填表结果 → 没填上 → 再试
  最多重试 N 轮
```

**这一课的一般化**：

1. **不要相信「返回 true 就代表成功」**——很多 API 的返回值只表示「我收到了参数」，不表示「事情做成了」
2. **定时器要用对层级**：`Handler` > `View.postDelayed` > `Thread.sleep`
3. **异步流程要有「确认」环节**：注入后必须回读结果，不能假设成功

### 6.5 ConnectivityManager：怎么问系统「现在用哪个网」

**概念**：Android 6.0 起，网络管理从「当前网络」变成「网络集合」。设备可能同时有 Wi-Fi、移动数据、VPN、蓝牙共享。

三个核心 API：

```java
// 1. 发起一个「网络需求」，系统回调告诉你现在满足这个需求的是哪个网络
NetworkRequest req = new NetworkRequest.Builder()
        .addTransportType(NetworkCapabilities.TRANSPORT_WIFI)  // 只要 Wi-Fi
        .build();
cm.registerNetworkCallback(req, callback);

// 2. 拿到 Network 对象后，查它的能力
boolean isWifi = caps.hasTransport(NetworkCapabilities.TRANSPORT_WIFI);

// 3. 把「当前进程」绑到这个网络
cm.bindProcessToNetwork(network);
```

**本项目落点**：`core/Net.java:81-104`（回调注册）、`Net.java:126-160`（`wifi()` 查找）、`Net.java:252`（`bindProcessToWifi`）。

### 6.6 `bindProcessToNetwork`：为什么这是必需的一步

**问题**：手机同时连着校园 Wi-Fi（未认证）和移动数据（已连通）。`HttpURLConnection` 会走**系统默认网络**——通常是移动数据。于是探测请求成功，看起来「已认证」，实际根本没用上校园网。

**解法**：

```java
ConnectivityManager cm = ...;
Network wifi = ...;                       // 从回调里缓存的 Wi-Fi Network
cm.bindProcessToNetwork(wifi);            // 这个进程的所有 socket 都走 Wi-Fi
```

绑定之后，**所有网络请求在 socket 层就被强制走 Wi-Fi**，即使 Wi-Fi 不通也不会自动切到移动数据（会直接失败，这才是正确行为）。

**关键细节：WebView 不走这个绑定**。这是 1.0.3 的新发现——WebView 的渲染进程有独立的网络栈，`bindProcessToNetwork` 管不到它。所以 `PortalActivity` 用了另一招：给 WebView 显式指定网络（Android 8.0+ 的 `WebView.setNetworkAvailable` 不够，实际要靠把 WebView 放在已经绑定的进程里，或者用 `WebResourceRequest` 拦截后自己发请求）。

**这一课的一般化**：**「进程级网络绑定」不是万能的**，每个网络栈（Java socket、WebView、native lib）可能各自独立。要逐个验证。

### 6.7 WifiManager 与 SSID：为什么读个 Wi-Fi 名字要定位权限

**背景**：`WifiManager.getConnectionInfo().getSSID()` 能读到当前 Wi-Fi 名。但这个信息**可以用来推断地理位置**（Wi-Fi 名称数据库 + MAC 地址 = 精确定位，精度比 GPS 还高，室内尤其好用）。

所以 Android 8.1（API 27）起：**读 SSID/BSSID 必须授予定位权限**，而且定位开关要打开。

```xml
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
```

**如果想只在授权后才做 SSID 过滤**：代码里先查权限，没有就跳过过滤逻辑（本项目 `onlyWifi` 和 `wifiSsidFilter` 就是这个结构）。

**更高版本的补充**：Android 10 起还有 `ACCESS_BACKGROUND_LOCATION`，后台读位置需要单独授权。Android 13 起 Wi-Fi 相关 API 又有变化（`WifiManager` 部分方法需要 `NEARBY_WIFI_DEVICES`）。

### 6.8 Doze 与电池优化白名单

**Doze 是什么**：屏幕关闭、设备静止、一段时间后，系统进入低电耗模式：**掐掉网络访问、推迟闹钟、禁止 JobScheduler**。

**对守护进程的致命影响**：探测请求每轮都超时（网络被掐），但定时器还在跑 → 不停唤醒 → 不停超时 → **又费电又不工作**。

**解法**：

1. **用户手动加白名单**：设置 → 电池 → 电池优化 → 找到 app → 不优化
2. **代码申请**：`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（需要声明 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 权限，Google Play 对它有审核限制）
3. **root 直接加**（本项目 `RootShell.enableBoost`）：

```bash
dumpsys deviceidle whitelist +$PKG      # 老版本
cmd deviceidle whitelist +$PKG          # 新版本
cmd appops set $PKG START_FOREGROUND allow   # 允许后台启动前台服务
```

**厂商二次限制**（这才是真麻烦）：

| 厂商 | 机制 | 应对 |
|---|---|---|
| 小米 | 神隐模式 / 自启动管理 | 手动开「自启动」+「无限制」 |
| 华为 | 应用启动管理 | 手动改成「手动管理」全开 |
| vivo/OPPO | 后台高耗电限制 | 手动加白名单 |
| 三星 | 电池优化 + 深度休眠 | 手动排除 |

**这一课的一般化**：**Android 的后台存活不是一个技术问题，是一组厂商策略的叠加**。任何「保活」方案都必须假设会被杀，设计成「能被重新拉起来」（本项目就是靠 `BootReceiver` + root 看门狗 + 前台服务三保险）。

### 6.9 SharedPreferences 与配置序列化

**概念**：`SharedPreferences` 是 Android 的键值存储，XML 格式，适合小配置（几 KB 到几百 KB）。

本项目在它上面又包了一层 `AppConfig`：

```java
public final class AppConfig {
    public String username = "";
    public String password = "";
    public int intervalSec = 60;
    // ...
    public JSONObject toJson() { ... }      // 导出配置用
}
```

为什么要包一层：

- **类型安全**：不用到处写 `prefs.getString("username", "")`
- **有默认值**：字段声明处就是默认值，一目了然
- **可序列化**：`toJson()` 支持导出/导入配置（换手机时不用重填）

**注意**：这里密码是**明文存在 SharedPreferences 里**的（`/data/data/<pkg>/shared_prefs/*.xml`）。在非 root 设备上其他 app 读不到，但 root 设备上任何 app 都能读。**生产级实现应该用 `EncryptedSharedPreferences`（AndroidX Security）**。本项目没做，因为目标设备用户自己 root 了——这是权衡，不是疏漏，但要写清楚。

**FileProvider**：Android 7.0 起禁止用 `file://` URI 跨 app 传文件（防隐私泄露）。导出诊断文件必须用 `content://`：

```xml
               android:resource="@xml/file_paths" />

```

**Gradle 构建**：

```gradle
android {

        versionCode 7         // 整数，只能递增，系统据此判断升级
        versionName "1.0.6"   // 字符串，给人看的
    }
}
```

`assembleRelease` 出的是**未签名包**（或已配签名的包）。签名用 keystore：

```bash
keytool -genkeypair -v -keystore release.keystore -alias campus -keyalg RSA -keysize 2048 -validity 10000
```

**签名的作用**：Android 用签名做「同一个 app」的认定。不同签名 = 不同 app，不能覆盖安装；相同签名 = 可以升级，且能共享数据。**丢了 keystore 就永远无法给已装用户升级**（只能卸载重装，数据全丢）。

## 7. 第六层：WebView 与 DOM 注入

这一层是为了对付「静态 HTML 解析拿不到」的门户（比如本项目 a79.htm，`<form>` 数量 0）。

### 7.1 WebView 的基本用法链路

```java
WebView wv = new WebView(ctx);
wv.getSettings().setJavaScriptEnabled(true);          // 必须开，否则脚本不跑
wv.setWebViewClient(new WebViewClient() {
    @Override public void onPageFinished(WebView v, String url) {
        // 页面加载完成（注意：这只代表 DOM 就绪，不代表 JS 渲染完）
    }
});
wv.loadUrl(url);
wv.evaluateJavascript(js, value -> { /* 回调拿到返回值 */ });
```

**几个必踩的坑**：

1. `setJavaScriptEnabled(true)` 默认是 **false**，忘了就是「脚本没反应」
2. `onPageFinished` 触发时，很多 SPA 页面还没渲染完（Vue/React 还在挂载）。要额外等或轮询
3. `evaluateJavascript` 必须在**主线程**调用
4. `evaluateJavascript` 的返回值是 JSON 编码的字符串，要二次解析
5. 页面跳转会重新创建 JS 上下文，之前注入的 hook 全丢

### 7.2 同源策略：为什么跨域 iframe 拿不到东西

**同源** = 协议相同 + 域名相同 + 端口相同。三者有任一不同就是跨域。

同源策略限制的是**JS 能读什么**：

| 操作 | 同源 | 跨域 |
|---|---|---|
| 读 `iframe.contentDocument` | ✅ | ❌ 返回 null / 抛异常 |
| 读 `iframe.contentWindow.document` | ✅ | ❌ 抛 SecurityError |
| `postMessage` | ✅ | ✅（唯一的合法跨域通信方式） |
| 加载 `<script src>` | ✅ | ✅（JSONP 的原理） |
| 发 `fetch` 并读响应 | ✅ | ❌（除非服务器给 CORS 头） |

**本项目的做法**（`assets/inject.js:242`）：

```javascript
var kids = safe(function () { return [].slice.call(doc.querySelectorAll("iframe,frame")); }, []);
for (var i = 0; i < kids.length; i++) {
    var w = safe(function () { return kids[i].contentWindow; }, null);
    if (!w) continue;
    var d = safe(function () { return w.document; }, null);   // 跨域这里会抛/返回 null
    if (!d) { rec("iframe 跨域，取不到 document"); continue; }
    scan(d);   // 递归进去
}
```

`safe()` 是个包装函数，把可能抛异常的调用包起来，异常时返回默认值。**这是写注入脚本的必备模式**——任何一处抛异常，整个脚本就停了。

**关键认知**：门户页如果把登录框放在**跨域** iframe 里，注入脚本**永远填不进去**。这不是技术难度问题，是浏览器的安全边界。这时候唯一的路是让用户在可见的 WebView 里手动操作（本项目 `PortalActivity` 就是干这个的）。

### 7.3 填表：为什么 `el.value = "x"` 经常没用

这是前端自动化最经典的坑。

**问题**：现代前端框架（Vue / React / Angular）不监听 DOM 的 `value` 属性变化，它们监听**事件**。而且很多框架会**重写 `value` 属性**，让它变成一个 getter/setter 对：

```javascript
// Vue 2 的做法（简化）
Object.defineProperty(input, 'value', {
    get() { return this._value; },
    set(v) { this._value = v; /* 不触发任何事件 */ }
});
```

所以 `el.value = "user"` 只是默默改了个内部变量，框架的状态（`this.username`）一点没变，提交时发出去的还是空字符串。

**正确做法**：绕过重写，直接调用**原生 setter**（`assets/inject.js:135`）：

```javascript
var d = Object.getOwnPropertyDescriptor(window.HTMLInputElement.prototype, "value");
d.set.call(el, "user");   // 直调原型上的原生 setter
```

`HTMLInputElement.prototype` 上的 `value` 描述符是浏览器原生的，框架重写的是**实例上的**属性。所以从原型链上取，能拿到没被污染的那个。

**然后还要派发事件**（第 140–143 行）：

```javascript
el.dispatchEvent(new Event("input",  { bubbles: true }));
el.dispatchEvent(new Event("change", { bubbles: true }));
el.dispatchEvent(new KeyboardEvent("keyup", { bubbles: true }));
el.dispatchEvent(new Event("blur"));
```

**为什么要发四种事件**：

| 事件 | 谁在听 |
|---|---|
| `input` | Vue 的 `v-model`（默认）、React 的 `onChange` |
| `change` | 原生表单、jQuery、很多老框架 |
| `keyup` | 监听键盘的老代码（有些校验逻辑挂这里） |
| `blur` | 失焦校验（「用户名已存在」这类检查） |

`bubbles: true` 是必须的——框架通常在容器上做**事件委托**，事件不冒泡就到不了监听器。

**还有一关**：React 用的是**合成事件系统**，它在 document 层挂了统一监听器。真实用户输入时浏览器会派发 `InputEvent`（`isTrusted: true`），而脚本派发的事件 `isTrusted: false`。有些严格的实现会检查 `isTrusted`，那就**彻底没辙**（脚本无法伪造 trusted 事件）。这时候只能靠 Hook（第 8 章）或者真实点击。

**本项目落点**：`inject.js` 里还额外发了一个 `keydown`（第 179 行）——因为有些登录框把「回车提交」绑在 `keydown` 上。

### 7.4 Hook XMLHttpRequest / fetch：请求取证

**目的**：不知道点登录后到底发了什么请求时，把请求拦下来记录。

**Hook XHR**（`inject.js:51`）：

```javascript
var oOpen = XMLHttpRequest.prototype.open;
var oSend = XMLHttpRequest.prototype.send;

XMLHttpRequest.prototype.open = function (m, u) {
    this.__url = u;                     // 把 url 存在实例上
    return oOpen.apply(this, arguments);
};

XMLHttpRequest.prototype.send = function () {
    var self = this;
    this.addEventListener("load", function () {
        rec("xhr " + self.__url + " -> " + self.status);   // 响应回来时记录
    });
    return oSend.apply(this, arguments);
};
```

**模式**：保存原函数 → 替换成自己的 → 在合适时机调原函数。这是所有 JS hook（以及 Xposed hook）的通用骨架。

**Hook fetch**（第 72 行）同理，注意 `fetch` 返回 Promise，要在 `.then` 里记录。

**怎么把数据送回 Java**：两种方式

1. `@JavascriptInterface` 注入一个 Java 对象，JS 里调 `window.AndroidBridge.log(msg)`
2. `console.log()` + 重写 `WebChromeClient.onConsoleMessage` 捕获

本项目用的是第 2 种（重写 `window.alert` 和 `console.log` 都要包，因为不同页面用不同方式报错）。

**安全提醒**：`addJavascriptInterface` 在 Android 4.2 之前是 RCE 漏洞（页面里的 JS 能反射调用任意 Java 方法）。4.2+ 要求加 `@JavascriptInterface` 注解，只暴露带注解的方法。**绝不要在加载不可信页面的 WebView 上暴露桥接对象**——门户页是学校控制的，但你不知道它有没有被入侵。

### 7.5 弹层文字抓取：为什么要抓这个

**问题**：登录失败时，门户往往弹一个 toast：「密码错误」「账号已锁定」「该账号已在别处登录」。这些信息**不在 DOM 的常规位置**，而是框架动态插入的临时节点。

**做法**（`inject.js:112`）：维护一组选择器，覆盖主流 UI 框架的弹层类名：

```javascript
var POPUP_SEL = [
    ".layui-layer-content",   // layui
    ".aui-toast",             // aui
    ".el-message",            // Element UI
    ".ant-message-notice",    // Ant Design
    ".toast", ".tip", ".msg", ".error", ".alert"
];
```

然后 `querySelectorAll` 全查一遍，把文字收集起来。同时包一层 `window.alert`：

```javascript
var oAlert = window.alert;
window.alert = function (m) { rec("alert: " + m); return oAlert.apply(window, arguments); };
```

**这是「取证思维」的体现**：当你不确定失败原因时，**先把所有可能的信号都收集起来**，而不是猜一个。1.0.5 加这个功能，就是为了回答「15:28 三次点击为什么不发请求」这个悬案。

### 7.6 定时器：轮询 vs MutationObserver

两种「等元素出现」的方式：

**轮询**（本项目用的）：

```javascript
var timer = setInterval(function () {
    if (doc.querySelector("#username")) { fill(); clearInterval(timer); }
}, 300);
```

优点：简单、兼容一切。缺点：有延迟（最多 300ms）、空转耗电。

**MutationObserver**：

```javascript
new MutationObserver(function (mutations) {
    if (doc.querySelector("#username")) { fill(); observer.disconnect(); }
}).observe(doc.body, { childList: true, subtree: true });
```

优点：实时、零延迟、不空转。缺点：`subtree: true` 在大型 DOM 上有性能开销；跨 iframe 要每个 document 各挂一个。

**为什么本项目选轮询**：因为要同时处理「页面还没加载」「iframe 还没创建」「框架还没渲染」三种情况，轮询是最不容易出错的。而且这是个一次性操作（填完就停），不是长期观察。

**判断标准**：一次性等待用轮询，长期观察用 Observer。

## 8. 第七层：Hook、Xposed 与 root（进阶）

### 8.1 Hook 是什么

**概念**：Hook = 在不修改目标代码的前提下，**在运行时替换或包裹一个方法**。

```
调用方  →  [方法入口]  →  方法体  →  [返回]
                ↑
            在这里插一脚
```

能做三件事：

1. **前插**（before）：方法执行前干点什么（记录参数、改参数）
2. **后插**（after）：方法执行后干点什么（改返回值、读 this 状态）
3. **替换**（replace）：整个方法体换掉

**原理（ART 虚拟机）**：每个 Java 方法在 ART 里对应一个 `ArtMethod` 结构体，里面有方法入口地址。Hook 就是**改这个入口地址**，让它跳到你的代码。你的代码做完事再跳回原地址。

这一步需要 root 或框架支持，因为要改的是**进程内存**。

### 8.2 Xposed / LSPosed 的模块加载流程

```
1. 系统启动 Zygote（所有 app 的父进程）
2. LSPosed 在 Zygote 里注入自己的代码
3. 每个 app fork 出来时，LSPosed 检查「这个包在哪些模块的作用域里」
4. 命中的话，加载模块的 dex，调用模块入口
5. 模块入口拿到目标 app 的 ClassLoader，开始 hook
```

**入口声明**：`assets/xposed_init` 文件，一行一个类名：

```
com.campusnet.autologin.xposed.XposedEntry
```

**入口实现**（`xposed/XposedEntry.java:27`）：

```java
public class XposedEntry implements IXposedHookLoadPackage {
    @Override
    public void handleLoadPackage(XC_LoadPackage.LoadPackageParam lp) {
        if (MODULE_PKG.equals(lp.packageName)) return;      // 别 hook 自己
        if (!matches(cfg.xposedTarget, lp.packageName)) return;  // 只 hook 配置的目标

        hookActivity(lp.classLoader, cfg);
    }
}
```

**`lp.classLoader` 是关键**：每个 app 有自己的 ClassLoader，加载的是自己的 dex。要 hook 目标 app 的类，必须用它自己的 ClassLoader：

```java
XposedHelpers.findAndHookMethod(
        "android.app.Activity", cl, "onResume", new XC_MethodHook() {
            @Override
            protected void afterHookedMethod(MethodHookParam param) {
                Activity act = (Activity) param.thisObject;
                // 页面出现后，检查是不是登录页，是就填表
            }
        });
```

**为什么 hook `Activity.onResume`**：这是「页面显示出来」的统一入口。不用管目标 app 用的是什么 UI 框架，任何界面显示都会走这里。

### 8.3 为什么 API 桩必须 `compileOnly`

**这是本项目最容易搞错、也最致命的一个工程细节。**

**背景**：写 Xposed 模块要 `import de.robv.android.xposed.IXposedHookLoadPackage`。但这个类**不在 Android SDK 里**，编译会失败。

**常见做法**：加一个 `xposed-api.jar` 依赖。但如果打成 `implementation`，这个 jar 就会进 APK 的 dex。

**为什么不行**：

1. **类冲突**：运行时 LSPosed 已经注入了一份 `de.robv.android.xposed.*`。如果 APK 里也有一份，ClassLoader 可能先找到你的那份，而你的那份是**空桩**（方法体是空的或抛异常），于是 hook 全部失效
2. **校验问题**：某些校验机制会把「包里带框架类」视为异常

**正确做法**：

```gradle
dependencies {
    compileOnly files("libs/xposed-api.jar")   // 只参与编译，不进包
}
```

**但模块自己的类必须在包里**：`XposedEntry`、`AutoFiller` 这些是模块代码，LSPosed 要靠 `xposed_init` 找到它们。如果也被排除掉，模块加载就崩。

**这两件事很容易混**：

| 类 | 归属 | 是否进 dex |
|---|---|---|
| `de.robv.android.xposed.*` | **框架**提供 | ❌ 绝不能进（compileOnly） |
| `com.campusnet.autologin.xposed.*` | **模块**自己的 | ✅ 必须在（否则模块找不到入口） |

**怎么验证**：用 `dexdump` 查 `class_defs`：

```bash
dexdump -f classes.dex | grep -i "Class descriptor.*xposed"
```

注意：`strings` 命令会误报——它会匹配到**字符串常量**里的类名引用（比如 `XLog` 的日志里写了类名），但那不是类定义。必须看 `class_defs` 段。

**这一课的一般化**：**「引用」和「定义」是两件事**。判断一个类有没有进包，要查类定义（`class_defs`），不是查字符串。

### 8.4 作用域（Scope）：为什么必须选对应用

LSPosed 的作用域机制是**安全边界**：

- 模块声明想 hook 哪些包（manifest 里或运行时配置）
- 用户在 LSPosed 管理器里**手动勾选**授权
- 只有被授权的包，LSPosed 才会在它的进程里加载这个模块

**为什么这么设计**：Hook 等于完全控制那个 app。如果没有授权机制，任何模块都能偷任何 app 的数据。

**本项目遇到的现实问题**：不知道学校的客户端包名叫什么。这就是 1.0.6 加「推荐应用」扫描的原因——**运行时扫描本机真实安装的应用**，按校园网特征打分排序，让用户勾选，而不是写死一批猜的包名。

**为什么不用 LSPosed 的静态「推荐作用域」**（`xposedscope` 声明）：那个机制要求在 manifest 里写**具体包名数组**。不知道包名就只能猜，猜错了要么不生效，要么**把账号密码填进别的应用的输入框**。宁可让用户点一下，不能瞎推荐。

**这一课的一般化**：**当你不确定的时候，把不确定性暴露给用户，而不是用猜测填平它。** 猜测填平的不确定性会在最坏的时刻爆炸。

### 8.5 root：`su` 与 shell 脚本

**`su` 是什么**：switch user。Android 上的 `su` 通常是 Magisk/KernelSU 提供的，调用时会弹授权框。

**Java 里执行 root 命令**：

```java
Process p = Runtime.getRuntime().exec(new String[]{"su", "-c", cmd});
```

**注意**：`su -c "cmd"` 里的 cmd 是**一整个字符串**，不是数组。所以参数拼接要注意转义，否则有命令注入风险（虽然这里命令是自己写的，但变量部分来自配置）。

**本项目的用法**（`root/RootShell.java`）：

1. **`enableBoost`**：加电池白名单 + 允许后台启动前台服务
2. **`startWatchdog`**：写一个 shell 脚本，循环检查 app 进程在不在，不在就拉起来

```bash
while true; do
    if ! pgrep -f com.campusnet.autologin >/dev/null; then
        am start-foreground-service ...   # 拉起来
    fi
    sleep 120
done
```

**为什么要这个**：因为厂商的省电策略可能把前台服务也杀掉。有个 root 看门狗在外面盯着，杀掉也能拉回来。

**代价**：`sleep 120` 的循环 = 每 2 分钟唤醒一次。虽然开销极小（纯 shell 阻塞，不占 CPU），但确实存在。

**这一课的一般化**：**root 能力是最后手段，不是首选**。它能解决「系统不让你干」的问题，但也让 app 变成了「必须 root 才能用」。所以本项目做成三条路线可选，而不是强依赖 root。

### 8.6 三条路线的设计哲学

这是整个项目最值得学的架构决策：

| 路线 | 依赖 | 能做什么 | 不能做什么 |
|---|---|---|---|
| A 纯 app | 无 | 直连接口、模拟表单、隐藏 WebView 填表 | 对付私有协议客户端 |
| B + root | `su` | 上面全部 + 看门狗保活 + 免电池限制 | 仍然进不了别的 app 的进程 |
| C + LSPosed | Xposed 框架 | 上面全部 + **hook 目标 app 内部** | 需要用户手动授权 + 重启 |

**关键设计**：三条路线**在同一个 APK 里**，互不冲突。不装 LSPosed 就是普通 app，装了也只是多一个能力。

**为什么不分开打包**：用户不需要为了试一个功能装三个 APK。而且同一个包名 = 共享配置 = 升级时数据不丢。

**这一课的一般化**：**能力应该是渐进增强的，不是二选一的。** 让用户从最低门槛开始用，需要更多能力时再加，而不是一上来就要求最高权限。

### 9.1 纯函数抽离：让核心逻辑能桌面测试

**问题**：Android 代码默认跑不起来单测——`android.util.Base64`、`Context`、`Log` 全都需要真机或模拟器。

**本项目的做法**：把**所有不依赖 Android 的逻辑**抽成零依赖的纯 Java 类：

| 类 | 依赖 | 桌面可测 |
|---|---|---|
| `SrunCrypto` | 纯 Java（自己实现 Base64） | ✅ |
| `EportalQuery` | 纯 Java（`Str` 也是纯的） | ✅ |
| `Judge` | 纯 Java（`Http.Result` 是 POJO） | ✅ |
| `Guard` | 纯 Java | ✅ |
| `Sanitize` | 纯 Java | ✅ |
| `AppRank` | 纯 Java | ✅ |
| `Jsonp` | 纯 Java | ✅ |
| `LoginVerdict` | 纯 Java | ✅ |

于是可以在电脑上跑：

```bash
javac -d /tmp/t -sourcepath app/src/main/java selftest/.../SrunSelfTest.java
java -cp /tmp/t com.campusnet.autologin.auth.SrunSelfTest
```

**为什么这个能力极其重要**：不用连手机、不用等构建（本项目一次 release 构建要几分钟）、不用面对「UI 点不出来」的问题。改了加密逻辑立刻能验证对错。

**本项目的自测覆盖**（一共 6 套，116 个断言）：

| `LoginVerdictSelfTest` | 11 | 登录结果文案解析（含「203」不是失败关键词的坑） |
| `SanitizeSelfTest` | 25 | 脱敏（密码、学号、IP、URL 参数） |
| `GuardSelfTest` | 34 | 凭据去处校验（8 个探测点 + 探测路径 + 正常门户） |

**怎么学这个**：写代码时问自己一句「**这段逻辑如果抽出来，脱离 Android 还能跑吗？**」能就跑。这不是为了测试而测试，是为了让逻辑本身更干净。

### 9.2 日志脱敏：单一出口原则

**问题**：诊断日志要发给别人看，里面不能有密码。但日志是**到处打的**，怎么可能保证每处都脱敏？

**答案：不要每处脱敏，要单一出口。**

```java
// core/Logx.java —— 唯一的写入口
public static void write(String level, String msg) {
    String clean = Sanitize.text(msg);     // ★ 所有日志必经此地
    ringBuffer.add(clean);
    fileWriter.write(clean);
    notifyUi(clean);
}
```

所有日志都走 `Logx.write`（或 `Logx.i/w/e`），`Sanitize.text()` 在这里统一处理。于是**无论谁在哪里打了什么，出口都是干净的**。

**脱敏规则**（`core/Sanitize.java`）：

| 内容 | 脱敏方式 |
|---|---|
| 密码 | 整个替换成 `***` |
| 账号 | 只留后 4 位：`****1234` |
| URL 里的 `user_password` 参数 | 值替换成 `***` |
| IP | 保留（诊断需要，且不算敏感） |

**这是本项目的血泪教训**：1.0.4 之前，15:10 那份诊断报告里带着**明文密码**，已经上传到云端了。加了脱敏之后，1.0.5 的诊断里搜不到密码。

**这一课的一般化**：**安全控制要放在「必经之路」上，不要放在「每个调用点」。** 后者一定会漏。

### 9.3 串行化：避免并发登录

**问题**：网络回调、定时器、用户点击，三个入口可能同时触发登录。如果并发，会出现「两次登录请求交叉，后一次把前一次的会话顶掉」。

**解法**：`LoginEngine` 内部串行化——一个 `AtomicBoolean` 或者单线程 executor，保证同一时刻只有一次登录在跑，后来的排队或直接返回。

### 9.4 指数退避：一个注释与实现不符的教训

**代码注释说**：「登录失败按 `retryBackoffSec` 指数退避」。

**实际实现**：

```java
next = Math.max(15, retryBackoffSec) * 1000;   // 固定 30 秒，没有递增项
```

**这是恒定频率重试，不是指数退避。**

**指数退避应该长什么样**：

```
第 1 次失败 → 等 30s
第 2 次失败 → 等 60s
第 3 次失败 → 等 120s
...
第 n 次 → min(30 * 2^(n-1), 上限)
```

**为什么指数退避重要**：

1. 失败往往是服务端的问题，高频重试只会加重它的负担
2. 电池：恒定 30 秒重试 = 一天 2880 次「12 秒超时」，这是本项目最耗电的状态
3. 反过来，成功后应该**重置**退避计数

**这一课的一般化**：**注释和实现会脱节，而且脱节的地方往往是要害。** 定期对着注释读实现，尤其是「重试」「超时」「退避」这类直接影响稳定性的参数。

### 9.5 幂等与状态收敛

**问题**：「守护」这个功能本质上是**周期性对账**——每 60 秒检查一次「现在应该在的状态」和「实际状态」是否一致，不一致就纠正。

**关键设计**：

- 检查本身就是幂等的（查一下不影响任何东西）
- 登录动作也是**幂等**的（已登录时再调一次登录接口，服务器返回「已在线」而不是报错）
- 状态判断只看**权威信号**（探测点的 204），不看自己的「上次登录成功」记录

**反面模式**（本项目早期犯过）：`onLost` 收到网络断开回调 → 立刻标状态为「已断开」→ 界面闪一下 → 下个回调又说连上了。**这是因为把「可能过期的信号」当成了权威。**

**修复**：`onLost` 时先回查 `Net.wifi()`，如果 Wi-Fi 还在，就只记一行日志，**不改状态**。

**这一课的一般化**：**回调是事件，不是状态。** 事件可能乱序、可能重复、可能过期。要从事件推导状态，必须**重新查询当前真实状态**，而不是直接相信事件的内容。

## 10. 学习路径

按依赖顺序，六个阶段。每个阶段给一个练手项目——**不做项目等于没学**。

### 阶段一：HTTP 与网络基础（1–2 周）

**目标**：能看懂任何一个 HTTP 请求/响应的每一个字节。

**要学**：
- 《HTTP 权威指南》（O'Reilly）第 1–4 章
- MDN 的 HTTP 文档（中文，质量很高）
- 状态码全表（不用背，会查就行）
- URL 编码、字符集（UTF-8 / GBK 的字节结构）

**练手**：用 `curl` 或 Postman，手写一个脚本登录任意网站（带 Cookie、带表单），能拿到登录后的页面。

**验证**：能用 `curl -v` 的输出现场讲出这个请求的每一行是什么意思。

### 阶段二：抓包与协议分析（1–2 周）

**目标**：能独立搞清一个陌生 app 的网络行为。

**要学**：
- Chrome DevTools 的 Network 面板（重点：Preserve log、Filter、Copy as cURL）
- `chrome://inspect` 远程调 WebView
- mitmproxy 基本用法 + 证书安装
- Wireshark 的 Follow TCP Stream

**练手**：抓一个校园网/酒店 Wi-Fi 的认证请求，把每个参数的含义推断出来（用第 4.3 节的方法：看值的变化规律）。

**验证**：能写出「这个参数是设备 IP，因为它的值和我在路由器上看到的一致」这种有理有据的推断。

### 阶段三：Android 基础（3–4 周）

**目标**：能独立写出一个带后台服务的 app。

**要学**（按顺序）：
1. Activity 生命周期（`onCreate`/`onResume`/`onPause`/`onDestroy` 什么时候触发）
2. 布局与资源（XML、`values/`、深色模式）
3. `SharedPreferences` / `FileProvider`
4. Service + 前台服务 + 通知渠道
5. `BroadcastReceiver`（开机自启）
6. Handler / Looper / 消息队列（**重点，这是 Android 异步的核心**）
7. `ConnectivityManager` / `WifiManager`
8. Doze 模式与电池优化

**推荐资源**：Android 官方文档（`developer.android.com`）的「应用基础知识」和「后台任务」两章。别看过时的博客——Android 的后台限制每两个版本就变一次。

**练手**：写一个「每分钟检查一次当前 Wi-Fi 名称并记录到文件」的 app，要求：锁屏后仍能工作、开机自启、有常驻通知。

**验证**：杀掉 app 后能自己回来；锁屏 30 分钟后日志还在写。

### 阶段四：WebView 与前端注入（2–3 周）

**目标**：能往任意页面注入脚本完成自动化操作。

**要学**：
- WebView 基本 API（`loadUrl`、`evaluateJavascript`、`WebViewClient`、`WebChromeClient`）
- 同源策略（这是前端的核心安全模型，必须吃透）
- DOM 操作（`querySelector`、事件、`MutationObserver`）
- **受控组件与原生 setter**（第 7.3 节，这是最容易卡住的地方）
- 事件派发（`dispatchEvent`、`bubbles`、`isTrusted`）
- 原型链与 `Object.getOwnPropertyDescriptor`

**练手**：写一个油猴脚本或注入脚本，自动填一个网站的表单并提交。要求能在 Vue/React 站点上工作。

**验证**：在 Vue 站点上，脚本填表后点提交，服务器收到的确实是填入的值（而不是空）。

### 阶段五：密码学基础（1–2 周，只需读懂）

**目标**：看到一段加密代码，能判断它属于哪一类、防住了什么、没防住什么。

**要学**：
- 对称加密（AES、TEA/XXTEA）的基本结构
- 哈希（MD5、SHA-256）与抗碰撞性
- HMAC 与长度扩展攻击
- Base64 与「编码 ≠ 加密」
- **不要学**：怎么设计密码算法（永远别自己设计）

**推荐资源**：《图解密码技术》（结城浩）——这本是入门最好的，讲的都是「为什么」而不是「怎么实现」。

**练手**：把本项目的 `SrunCrypto` 读懂，用 Python 独立实现一遍，然后和 Java 版对拍（同样输入必须同样输出）。

**验证**：能解释「为什么深澜要两阶段认证」「为什么 HMAC-MD5 现在还算安全」。

### 阶段六：Hook 与系统层（进阶，按需）

**目标**：能用 LSPosed 写一个能用的模块。

**要学**：
- Java 反射与 ClassLoader
- ART 方法调用机制（`ArtMethod`、方法入口）
- Xposed API（`findAndHookMethod`、`XC_MethodHook`）
- 作用域机制
- `compileOnly` 与打包边界（第 8.3 节）

**练手**：写一个模块，hook 某个 app 的某个方法，把参数打出来。

**验证**：模块能在目标 app 里正常加载，日志能看到参数，且 APK 的 dex 里没有 `de.robv.android.xposed` 的类定义。

### 学习顺序的一句话总结

```
HTTP → 抓包 → Android 基础 → WebView/DOM → 密码学 → Hook
 ↑                                              ↑
 最先学，一切的基础                        最后学，因为前面都会了才用得上
```

**别跳阶段**。跳过 HTTP 直接学 Hook，你会写出一堆「能跑但不知道为什么」的代码，遇到问题无法定位。

## 11. 这个项目的 12 个 bug，就是 12 堂课

这是最值得反复看的一节——**每个 bug 都对应一个知识点，而且是真实发生过的**。

| # | bug | 根因 | 对应知识 | 一般化教训 |
|---|---|---|---|---|
| 1 | 猜成 Dr.COM | 资料库信息和实际部署不符 | 协议逆向 | 任何「某厂商就是 XX 协议」都是危险简化 |
| 2 | 203 Bad request | 端口/路径/方法全猜错 | HTTP 与逆向 | 猜测的上限是「看起来合理」，抓包才是证据 |
| 3 | 203 反复出现 | 把 a79.htm（页面）当登录接口 | 阶段区分 | 「页面」和「接口」是两个东西，别看错 |
| 4 | 开流量时显示已登录 | 探测请求走默认网络（移动数据） | Android 网络 | 「能上网」≠「Wi-Fi 认证通过」 |
| 5 | `error` 被判成失败 | 裸关键词误命中 `Error code: 203` | 字符串匹配 | 子串匹配必须考虑上下文，别用裸关键词 |
| 6 | 填表脚本从未执行 | 未 attach 的 WebView 上 `View.postDelayed` 进静态 RunQueue | Handler/View | 返回 true 不代表成功，静默失败最难查 |
| 7 | 脚本执行了但没填上 | 页面 JS 还没渲染完 | 异步时序 | 异步操作要有「确认」环节，不能假设 |
| 8 | 跨 frame 填不上 | 脚本只在顶层 frame 跑 | 同源策略/iframe | 登录框可能在子页面里，要递归 |
| 9 | 密码泄露到诊断 | 日志无统一脱敏出口 | 安全设计 | 脱敏要放在必经之路，不是每个调用点 |
| 10 | 密码发到小米服务器 | 探测失败时落点被当成门户 | 凭据去处校验 | 提交凭据的出口必须默认拒绝 |
| 11 | Wi-Fi 假断开 | `onLost` 收到已过期的 Network | 事件 vs 状态 | 回调是事件不是状态，要回查真实状态 |
| 12 | 「指数退避」不存在 | 注释与实现脱节 | 工程严谨 | 注释会腐烂，重试/超时参数要对着读 |

**怎么用这张表学习**：挑一个 bug，假装自己是当时的我——只有现象，没有根因，你会怎么定位？然后对照「根因」看自己的思路差在哪。

**这 12 个 bug 的共同模式**（比单个 bug 更重要）：

- **7 个是「以为成功了其实没有」**（1、3、4、6、7、8、11）→ 都要**回读验证**
- **2 个是安全相关**（9、10）→ 都出在「出口没守住」
- **3 个是「猜 vs 实测」**（1、2、5）→ 都要**拿证据**

## 附：一张速查图

```
┌─ 判断「在不在线」 ────────────────────────────────┐
│ 1. Wi-Fi 有吗？没有 → 不在线（不管流量通不通）      │
│ 2. 探测点回 204 吗？是 → 在线                      │
│ 3. 回 302 吗？→ 被劫持，未认证                     │
│ 4. 回 200 但内容是 HTML？→ 被劫持，未认证           │
│ 5. 超时/失败？→ 网络异常，不是「未认证」            │
└───────────────────────────────────────────────────┘

┌─ 判断「该走哪条认证路线」 ────────────────────────┐
│ 1. 有抓到的直连接口？→ 直连（最快，1~2 个请求）     │
│ 2. 门户页有 <form>？→ 模拟表单提交                 │
│ 3. 只有 iframe / JS 渲染？→ 隐藏 WebView 填表      │
│ 4. 都失败？→ 手动门户页（用户自己点）              │
│ 5. 有 LSPosed？→ 直接 hook 官方客户端              │
└───────────────────────────────────────────────────┘

┌─ 判断「凭据能不能发」 ────────────────────────────┐
│ 目标是探测点（小米/Google/Apple/微软/高通/vivo/华为）？→ 拒 │
│ 目标是探测路径（generate_204 等）？→ 拒            │
│ 目标是探测点主机？→ 拒                             │
│ 其他 → 放行                                        │
└───────────────────────────────────────────────────┘
```
